# 探针技术详解

## 1. 什么是探针

探针（Probe / Instrumentation，埋点/插桩）就是在**不改业务逻辑**的前提下，
在代码的关键路径上临时放置一个观测点：把"此刻变量的值、耗时、调用顺序、
收到的字节"暴露出来，让原本不可见的运行时行为变成可读的事实。

与断点调试的区别：

| | 断点调试 | 探针 |
| --- | --- | --- |
| 干扰程度 | 冻结整个进程 | 进程照常跑（时序类 bug 必须用它） |
| 覆盖 | 一次只看一个瞬间 | 可连续观察、可留档对比 |
| 场景 | 逻辑分支想不清楚时 | 偶发问题、时序问题、通信问题、界面问题 |

**特重要的一点：时序类 bug（通信粘包、竞态、超时）在断点下根本复现不了**，
因为断点一停，对端早就超时或重发了。这类问题只能靠探针。

## 2. 探针和日志的区别（常被混用，实为两种工具）

一句话定位：**日志是黑匣子，探针是听诊器**。

| 维度 | 日志 | 探针 |
| --- | --- | --- |
| 出发点 | 先猜"以后可能出什么事"，提前铺点 | 已有一个具体问题，现在就要答案 |
| 生命周期 | 常驻代码，随版本长期演化 | 临时植入，问题解决立即删除 |
| 内容 | 讲一个完整的故事（时间轴、事件序列） | 察一行具体的事实（某个值的真实样貌） |
| 量级 | 必须克制：级别过滤、防日志洪水 | 可以放肆：本机临时打印，随删除消失 |
| 面向的对象 | 未来的自己/运维，事后翻现场 | 正在现场排查的工程师，边插边看 |
| 形态 | 统一组件：级别+来源+时间戳+结构化 | 通常就是一行打印/一个临时断言，没有"框架" |
| 典型反例 | 想挖深一点时发现"当年没记这个值" | 排查完忘了删，僵尸探针变成日志噪音 |

几点最容易混淆的实质差别：

1. **方向相反**。日志是"预防性"的——你必须在不知道会不会出事的时候决定
   记什么，赌的是重点；探针是"应答式"的——问题已经发生且聚焦，你带着明确
   的问号去问系统要一个值。这也是为什么日志永远"少记了关键一条"，而探针
   永远是排查到一半再加的。
2. **信噪比策略相反**。日志要忍受"99% 时间用不上"的成本，所以必须按级别
   过滤、控制体积；探针为了回答眼前一个问题可以往循环里逐字节打帧，因为
   它活不过今天——代价是**必须有删除纪律**（见 §6），否则就退化成垃圾日志。
3. **两者互相转化，而不是竞争**。
   - 探针 → 日志：临时探针验证出的观测点，如果对长期运维有价值
     （比如通信超时前后的状态），就"沉淀"为带级别和来源的正式日志；本项目的
     统一报警服务就来自一次临时报警演示探针的常驻化。
   - 日志 → 探针：排查从日志入手，但日志只能告诉你"在哪个时间点附近出的事"，
     要回答"那个瞬间变量到底是多少"，必须在日志圈出的范围里再插临时探针。
4. **判断该用哪个的口诀**：
   - 问"刚才发生了什么/多久会发生一次" → 要日志；
   - 问"现在这一行代码拿到的值究竟是多少" → 要探针。

日志是十类探针中唯一会常驻的形态（详见 §5.6"日志探针"），其余九类都是
临时兵器——这正是本章节存在的意义：**别把刀常留在案板上，也别拿黑匣子当听诊器敲**。

## 3. 为什么有效

绝大多数"玄学 bug"的本质是：**我们的心智模型和机器的真实行为不一致**。
排查就是在收集证据，让事实淘汰错误假设。探针提供的是第一手运行时证据，
比"看着代码猜"效率高一个数量级。

排查心法（每个探针对应一次假设检验）：

1. 先写下一个具体的问题（不能笼统，"为什么不对"不行，
   "主站发出去的第 8 个字节到底是 0x03 还是被数据覆盖了"才行）；
2. 设计一个能回答这个问题的最小探针；
3. 植入 → 运行 → 采集 → 回答；
4. 得到答案后，问题通常立即收敛为下一个更小的问题；
5. **探针完成使命立即删除**，不留进最终构建。

## 4. 观测通道：值是怎么到排查者眼里的

探针打了点只是第一步，还得选对**采集通道**，让值真正流进观测者的视野。
核心问题是：**被观测的进程是谁的？** 这决定了值的去处，也是"打印还是记日志"
这个常见疑问的答案来源。

### 4.1 自己起的进程 → 控制台 stdout（临时探针首选）

headless 探针（临时控制台工程）由排查者直接启动，`Console.WriteLine`
的输出**直接出现在进程标准输出里，当场可读**：

```
[SLAVE] RX 完整帧: 00 01 00 00 00 06 01 03 00 00 00 02
[SLAVE] 解析: 事务号=1 协议号=0(应=0) 长度=6 单元=1 功能码=0x03
```

本项目 Modbus 组帧 bug 的定位就是这样：伪从站把主站发来的 12 个字节
打印在 stdout 上，与协议文档逐字段对照，少 1 字节一目了然。
演示工程（Demo3）走的就是这条通道。

注意 CI/管道场景：进程被重定向捕获时 stdout 是否行缓冲，会影响
"能不能实时看到"（见 §7 陷阱）。

### 4.2 不能控制的长活进程 → 落盘日志（常驻探针首选）

WPF 主程序、Windows 服务这类进程**没有控制台，Console.WriteLine
全部静默丢失**（§7 第一个陷阱）。对它们只能走文件：统一日志组件带
级别/来源/时间戳落盘，事后由排查者读文件还原时间轴。

本项目实践：报警/连接状态/异常接入 HTLog 写
`bin\Debug\net48\Log\日期\`，偶发通信超时的事发现场从日志文件按
时间轴还原。**间歇性问题唯一的机会在下一次发生时，所以这条通道必须平时就位。**

### 4.3 渲染结果 → 截图

界面问题的"值"不以文本存在（颜色、布局、弹出行为），临时探针是
PrintWindow/系统截图，直接看渲染结果。本项目验证报警抽屉的
分色与自动弹出即用此法。

### 4.4 控件状态 → UI Automation

需要拿结构化值（控件文本、位置、是否可见）时，用 UIA 读属性树，
返回的是纯文本，可 grep、可比对。

### 4.5 选择口诀

| 问题 | 通道 |
| --- | --- |
| 我自己起的进程，要当场看值 | stdout 打印（临时探针） |
| 进程不是我能控制的/要等人来翻 | 落盘日志（常驻探针） |
| 值是"长什么样"而不是"是什么" | 截图 |
| 要结构化的控件/系统状态 | UIA / 系统查询 |

对应 §2：**临时探针优先 stdout（快、当场可读、反正会删），
常驻观测才写日志（要看守现场等人来翻）**。

## 5. 探针种类与实际应用场景

按"要回答的问题"选探针种类，而不是反过来。速查：

| 症状 / 疑问 | 该用哪种 | 对应示例 |
| --- | --- | --- |
| 分支没进、值中途变了 | 5.1 变量/路径探针 | — |
| 慢，但不知道慢在哪一段 | 5.2 耗时探针 | ProbeScope.cs |
| 通信"理论上没错"但设备不回 | 5.3 通信帧探针 | FakeModbusSlave.cs |
| 界面没反应/颜色不对 | 5.4 UI 观测探针 | （截图+UIA+演示代码） |
| 疑问在逻辑层，想甩开 UI 验证 | 5.5 Headless 探针 | 本演示工程本身 |
| 事后要还原"当时发生了什么" | 5.6 日志探针 | — |
| 流程卡死、状态莫名跳变 | 5.7 状态机探针 | StateMachineProbe.cs |
| 事件频率异常（风暴/漏发） | 5.8 频次探针 | RateProbe.cs |
| 内存/句柄只涨不掉 | 5.9 资源探针 | ResourceProbe.cs |
| "谁改了我的配置/这个字段" | 5.10 快照对比探针 | SnapshotProbe.cs |

### 5.1 变量/路径探针（最常用）
在可疑路径打点，输出关键变量的值，用"走到了没有、值是什么"快速二分定位。
适合：条件分支不进入、值中途被改、解析结果为空。

```csharp
// [PROBE 临时] 验证：IsValid 为什么是 false
Trace.WriteLine($"[PROBE] IsValid={IsValid}, row.Count={row?.Count ?? -1}, expected={expected}");
```

### 5.2 耗时探针
Stopwatch 打点，定位"慢在哪一段"。推荐封装成 IDisposable 作用域探针
（见示例工程 `Probes/ProbeScope.cs`）：

```csharp
ProbeScope.Run("加载配方", LoadRecipe);     // 自动打 进/出/耗时/异常
```

实际应用：本项目把"打开串口 → 载入点位表 → 建立连接"整条启动链
逐段 Measure，一眼看出慢在 SPI 参数下发而不是 SQL 查询。

### 5.3 通信帧探针（协议调试专用）
把收发的**原始字节**按十六进制打出来，对着协议文档逐字节核对。
示例：收到请求帧 `<00 01 00 00 00 06 01 03 00 00 00 02>`，
一眼可核：事务号 0001、长度 0006、从站 01、功能码 03、起始 0000、数量 0002。
本项目 ModbusTcpMaster 组帧 bug（少 1 字节、长度字段少 2）就是靠这类探针
回环对帧定位的（见示例工程 `Probes/FakeModbusSlave.cs`）。

```csharp
ConditionalProbe.Frame("RX", response);   // [PROBE 收 <<< 7B] 01 03 04 12 34 56 78
```

### 5.4 UI 观测探针
界面问题的"探针"是三个手段的组合：
- **截图**（PrintWindow 拿真实渲染结果）；
- **UIA（UI Automation）树**（取控件属性、位置、文本）；
- **临时演示代码**：怀疑"事件没到 UI"时，在订阅回调里临时画一条
  固定文字/时间戳，界面上出现了 → 通道是通的，问题在数据；没出现 → 问题在事件。
  本项目报警抽屉验证就是这么做的：临时 DispatcherTimer 每 5 秒报一次
  "探针演示"，截图确认分色与弹出，然后删除。

### 5.5 编译/Headless 探针
不启动 UI，用最小工程把纯逻辑层（协议、解析、服务）链接进来直接跑。
适合：让逻辑验证不依赖界面、数据库、硬件，也方便塞进以后的单测。
本项目做法：临时 net8 控制台 csproj，`<Compile Include>` 绝对路径
引用现有源文件，跑完删工程——桌面这套演示工程正是这个形态的成熟版。

### 5.6 日志探针
正规长期的探针形态。区别于临时打印的要点：**带级别、带来源、带时间戳**，
事后能从日志文件还原事发序列。异常钩子（AppDomain.UnhandledException、
Application.DispatcherUnhandledException、TaskScheduler.UnobservedTaskException）
是最值得常驻的三个"永久探针"。
（如何取舍"值得常驻的"，见 §2 的转化口诀。）

### 5.7 状态机探针（示例工程 `Probes/StateMachineProbe.cs`）
**症状**：自动流程"停在第 4 步不动了""没报错就直接跳到结束"。
**原理**：每次进入新状态记录 迁移对 + 滞留时长；配一张合法迁移表，
非法迁移当场点名；历史序列可事后 Dump 还原"卡死前走过的路"。

```csharp
var sm = new StateMachineProbe<DeviceState>("主流程", IsLegal);
sm.OnEnter(DeviceState.Loading);
// 输出：[STATE:主流程] Idle -> Loading（Idle 滞留 130ms）
// 输出：[STATE:主流程] !! 非法迁移：Running -> Idle
```

**为什么不用断点**：自动流程挂着对端设备，断点一停，下位机早就超时重试了，
状态流全被打乱——只有不干扰时序的状态机探针能看到真序列。
**变体**：把 UI 事件的迁移（导航跳转）、弹窗生命周期也能套同一套探针。

### 5.8 频次探针（示例工程 `Probes/RateProbe.cs`）
**症状**：报警每秒刷几百条（风暴）？心跳 5 秒没来（漏发）？按钮连击
触发重复命令？——先拿数字再下结论。
**原理**：滑动窗口计数，每满一个窗口自动打印 次数/速率。

```csharp
var hb = new RateProbe("下位机心跳", windowMs: 1000);
hb.Hit();   // 每次心跳调用；满窗自动打印 [RATE:下位机心跳] 近 1.0s 共 9 次
```

**实际应用**：本项目曾用"帧率探针"确认 TCP 断线重连风暴——重连逻辑
每 200ms 重试一次把电磁阀端 MCU 打挂，日志只写"连接失败"看不出频率。
**纪律**：`Hit()` 本身要上是 `[Conditional("PROBE")]`，Release 里
连计数都不发生，更不要谈开销。

### 5.9 资源探针（示例工程 `Probes/ResourceProbe.cs`）
**症状**：程序过夜内存涨了几百 MB；TCP 反复插拔后句柄只增不减；
拍照后线程数暴涨不回落。
**原理**：定时（或关键节点）采样打印 内存/私有提交/句柄/线程/GC 代数/托管堆，
**多次采样看斜率**——"泄漏"的定义是斜率不是绝对值。

```csharp
ResourceProbe.Sample("压测前");
RunStress(); 
ResourceProbe.Sample("压测后");
// 对比：私有提交 8MB -> 38MB，句柄 259 -> 261（句柄正常，托管在涨）
```

**实际应用**：本项目排查"相机连拍后内存上涨"，靠句柄数不涨 + 托管堆涨
两条证据把嫌疑从"Bitmap 没 Dispose"收窄到"图像缓存列表只进不出"。

### 5.10 快照对比探针（示例工程 `Probes/SnapshotProbe.cs`）
**症状**："波特率不知道什么时候从 9600 变成了 19200""这个标志位谁翻的？"
——单点日志只能看到"已经变了"，看不到"在哪一步变的"。
**原理**：可疑方法执行前 Dump 一份对象属性快照、执行后再 Dump 一份，
diff 逐字段点名变更/新增/消失。

```csharp
var before = SnapshotProbe.Dump(config);
SuspiciousInit(config);
SnapshotProbe.Compare("AmpConfig", before, config);
// [SNAP:AmpConfig] BaudRate: 9600 -> 19200
// [SNAP:AmpConfig] TimeoutMs: 3000 -> 800
```

**实际应用**：本项目排查 modbus.json 设置被改，Compare 一次 diff
就把"ApplySettings 顺手覆写了 Transport 字段"钉死。
**变体**：不只对象属性——数组快照（长度+前 N 元素）、字典快照、
甚至两张表的行数，都是同一思想的实例。

## 6. 植入纪律（血泪约定）

1. **带问题出生，完成即删**：留探针 = 留噪音。合入前的构建里不该有
   任何探针痕迹。
2. **显式标记**：探针代码行统一加注释标记，例如
   `// [PROBE 2026-11-06 zouj] 临时：验证 xxx，验证后删除`
   ——搜索 `[PROBE` 就能枚举全部探针，防止遗漏清理。
3. **不动语义**：探针绝不能改变执行路径（不要顺手修 bug，不要 try/catch 吞掉
   探针自己的异常然后假装没事）。
4. **输出要机器可辨**：统一前缀（如 `[PROBE]`），日志里 grep 一下全出来；
   帧数据用十六进制并带方向（TX/RX）与事务号。
5. **一次只回答一个问题**：不要一口气埋二十个点，信号淹没在噪音里。

## 7. 常见陷阱

- **Console.WriteLine 在 WPF/服务里看不见**：进程没有控制台时输出静默丢失，
  改用 `Trace.WriteLine`（注意先挂 TextWriterTraceListener，示例工程
  Program.Main 即是）或日志组件。
- **探针自己改变时序**：在探针里 Sleep/弹窗，把它要观察的竞态掩盖了——
  这是"加日志就好了，删日志就复发"的经典来源。
- **字符串拼接在关闭路径上也执行**：高频路径先 `if (probeEnabled)` 再拼，
  或用 `[Conditional]`（编译期剥除，零开销，见 ConditionalProbe.cs）。
- **忘了删**：用上面的 `[PROBE]` 标记 + 提交前全局搜索兜底。
- **只打印不对比**：探针值要和"期望值"对照着看，否则只是换了个地方发呆。
